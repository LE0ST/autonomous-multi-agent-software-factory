## Smallest source slice that can be separated now

**Pure P15 canonical parser/renderer plus explicit expected-value comparisons.** This has no file, token, process, service, pipe, ACL or ETW operation. It consumes the fixed six-field grammar, exact run/case constants, supplied P10/P11 expectations and an opaque generation value. It validates/returns owned data; it cannot establish provenance, allocate a generation, select a case, admit a lifecycle or construct a trusted production binding from arbitrary caller data.

Why first: its canonical bytes are already determinate and it has no dependency on the disputed process baseline, P14 SDDL representation, startup observation or live invalidation mechanism. It is a useful prerequisite of both A2 and A3 selected-case readers. It has a smaller authority and native dependency surface than starting with the collector or complete endpoint comparator.

The [matrix](IMPLEMENTABILITY_MATRIX.md) also identifies a separable A2 process observation/comparison helper. It can compare explicit trusted PID/start/path expectations to an acquired connection/process without selecting an invalidation policy. Its result cannot be called complete endpoint authentication. It need not precede the pure P15 slice and does not unblock native transport by itself.

No source is implemented by this review. The readiness finding is scoped to these bounded interfaces; it does not accept the entire P14/P15/ACE proposal.

## Dependency-derived sequence after correction

1. **Pure P15 contract.** Implement/review only the syntax and explicit comparisons above. Preserve accepted result-ownership/immutability principles; no new trusted-input carrier.
2. **P15 protected reader seam after F3/F5.** Use explicit trusted root/P1/P3/P15 and associated P11/lifecycle inputs. Both A2 and A3 get the same validation obligations. The accepted P11 custody reader remains unchanged and still requires independent P11 metadata/seal. Actual provisioning is separate.
3. **Pure P14 contract after F2.** Freeze exact descriptor encoding and bounded canonical record validation, parameterized by explicit static expectations. No collector or “authenticated” result is implied by parsing.
4. **P14 protected reader and publication interfaces after F3/F5.** Bind fixed child bytes to trusted creation metadata and the specified admission lifetime. Reader implementation does not need a live collector; producer implementation must obey the reviewed publication commit and failure rules.
5. **Process setup/readback helper after F1; bounded A2 process comparator.** These are independent source units. Setup validates the permitted baseline and exact final descriptor before pipe creation. Comparator uses only the proposed limited mask and retained process handle. Neither proves token denial or full endpoint authenticity on an uncommissioned host.
6. **Broker startup telemetry/lifetime source and BA collector after F4 and their dependencies.** Review emitter ordering/identity/handle retention, session attribution and loss handling, independently checked process/P6 facts, P14 writer and post-publication duty as explicit responsibilities. Collector acceptance cannot precede a reviewed emitter contract and process setup behavior. This is still source work, not permission to run ETW or start a service.
7. **A2 endpoint gate / A3 connection gate / transport integration.** Only after the relevant readers, emitter/collector, process checks and F3 lifecycle gate are accepted. Compose with the already accepted codec/correlation validator, nonce, authority binding and fixed P11 read. Requests cannot select P11 state; responses cannot update either protected record.
8. **Separate later gates.** Complete G1 source/manifests and independent review. Only independently authorized G2 may establish actual resource identities, access results, token denial and two-case commissioning. G3 remains separate. This review grants neither gate.

The order is a dependency order, not a claim that every independent helper must wait for unrelated host values. Steps 2, 3 and 5 can be separately reviewed once their own design inputs are closed. The collector has the largest dependency set and should not be used to invent those inputs during implementation.

## Acceptance boundaries to retain

- Pure parser success means canonical data and explicit equality checks only.
- Protected reader success means the held object matches trusted metadata/content under its specified observation window.
- Process comparator success means the connected-process observations match explicit expectations during the checked handle lifetime.
- Collector success means the specified independently anchored startup observation and publication protocol completed.
- Endpoint authentication additionally requires the complete current-lifecycle binding and retirement/acceptance rule.

Collapsing these meanings would reintroduce the bootstrap ambiguity this review is intended to expose. Keeping them explicit allows small source reviews without pretending that an unresolved production authority path has been implemented.
